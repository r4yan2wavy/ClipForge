# Upload setup, recovery, and verified platform facts

Primary documentation checked October 18, 2026. Platform settings can change; inspect the project's current Google Cloud Console quotas and the channel's actual eligibility before enabling uploads.

## Quotas and upload restrictions

The current quota calculator gives `search.list` and `videos.insert` separate default buckets of 100 calls each per day, costing one unit per call. Other endpoints share 10,000 daily units by default; daily resets use Pacific Time. Each pagination request consumes quota. These are published defaults, not a promise about a particular project. [Official quota calculator](https://developers.google.com/youtube/data/determine_quota_cost).

The current insert reference, updated October 15, 2026, explicitly says unverified API project uploads are **not restricted to private viewing**. Older private-only descriptions should not be repeated as current rules. Account settings and upload limits still matter; this starter explicitly defaults to private as its own production choice. Uploads require owner OAuth; an API key identifies a discovery project but cannot authorize channel uploads. [Official videos.insert reference](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert?hl=en).

## One-time owner consent and credential storage

Enable YouTube Data API v3, configure the consent screen/test users as applicable, create a **Desktop app** OAuth client, and place its downloaded JSON at the configured `upload.client_secrets` path. Set the exact intended channel ID first. The `authorize` command uses Google's installed-app consent with PKCE and a loopback callback; the ordinary system browser opens for the owner to approve. This is interactive consent, not browser automation. [Official desktop OAuth guide](https://developers.google.com/identity/protocols/oauth2/native-app).

Requested scopes are `youtube.upload` plus `youtube.readonly`. The latter permits owner channel verification and status polling. `channels.list(mine=true)` must identify exactly the configured channel before this program starts an insert. If the wrong Brand Account/channel was selected, repeat authorization with the right channel. The starter deliberately rejects ambiguous multiple-channel results rather than choosing one. [Official channels.list reference](https://developers.google.com/youtube/data/reference/rest/v3/channels/list).

Offline refresh credentials are saved atomically at `upload.token_file`. Google notes that external consent applications in **Testing** issue refresh tokens expiring after seven days when using scopes such as YouTube's; the narrow identity-only exception does not cover these scopes. Tokens can also stop working after revocation, inactivity, or other account/policy changes. A successful production consent configuration does not make tokens immortal. The program refreshes supported credentials and returns `auth_required` when renewal fails; authorize again when appropriate. [Official token expiration guidance](https://developers.google.com/identity/protocols/oauth2#expiration).

Protect the entire `secrets/` and `data/` directories, including SQLite WAL/SHM files and backups, with user-only OS permissions and preferably full-disk encryption. Session URIs are sensitive. POSIX token creation uses mode 0600. On Windows, configure an NTFS directory ACL limited to the scheduler's user account; `chmod` alone does not implement that ACL. Secrets and state files must stay out of public repositories and shared output packages. Do not enable verbose HTTP debug logging. This is local file storage, not an encrypted credential vault.

## Scheduling and declarations

`status.publishAt` requires a never-published private video; a past value can publish immediately. Therefore the starter rejects naive/past times and requires configurable processing lead time, normalizes the instant to UTC, and always sends private with a schedule. Processing lead time is an operational preference, not a completion guarantee. `processingDetails` is owner-only data; processing can fail independently of upload acceptance. The worker later checks actual privacy/publication state instead of assuming that an accepted upload became public. [Official video status and processing properties](https://developers.google.com/youtube/data/reference/rest/v3/videos?hl=en).

For New York schedules, supply the intended explicit UTC offset, for example `2030-01-15T09:00:00-05:00`. Winter and summer offsets differ. At the autumn clock change, 01:30 occurs twice; select its offset deliberately. At the spring change, some local clock times do not exist. No code silently attaches a zone to an ambiguous naive value. The configured display timezone is `America/New_York`; persisted upload instants use UTC.

`made_for_kids` and `contains_synthetic_media` must be explicit human-configured booleans in the manifest or upload configuration. No keyword/LLM heuristic sets them. Audience designation depends on the intended audience and relevant factors; general family suitability alone is insufficient. [Official audience guidance](https://support.google.com/youtube/answer/9528076?hl=en).

The current disclosure guide requires disclosure for realistic generated or meaningfully altered content and describes exceptions for minor production assistance, including caption creation. Read its current examples for the actual footage and music. AI-assisted clip selection or metadata by itself does not determine the declaration. [Official GenAI disclosure guidance](https://support.google.com/youtube/answer/14328491?hl=en).

## Duplicate prevention and manual reconciliation

The raw resumable protocol is a deliberate substitution for the high-level upload helper: SQLite must durably store the URI and acknowledged offset between separate process runs. Authentication still uses supported Google libraries. Google documents empty status-query PUTs, recovery of the completed response, acknowledged `Range` values, expiring sessions, and 256 KiB chunk multiples. [Official resumable upload protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol).

The unique `(clip_id, channel_id)` record preserves checksums, complete preparation inputs and versions, upload metadata, reserved UTC schedule, session URI, offset, video ID, and separate processing/publication states. A `ready` intention is saved before OAuth checks, then enters `initiating` immediately before the first insert. The returned session is saved before any media bytes are sent. Every media request commits intent before sending. Restarts probe an existing session before resuming. An uncertain final response is resolved by probing that same session. A definite rejected 4xx insert can be retried using the existing intention record; an uncertain insert or final outcome never creates another automatic insert.

An expired/missing session, missing completion ID, or changed preparation inputs routes to `needs_reconciliation`. This policy is deliberately more conservative than the transport guide's suggestion to start again after expiration: a completed upload may already exist. There is no YouTube upload idempotency key and no exactly-once guarantee.

To reconcile, keep the worker stopped for that clip and inspect the authorized channel's YouTube Studio uploads and local record using clip metadata, time, and file details. Do not rely on the title being unique. Confirm the actual video ID and intended channel before an operator repairs a record. Do not delete the row or clear its URI just to get the worker running: that defeats duplicate protection. The starter exposes safe inspection output but leaves uncertain record repair as a documented operator task. An API response is not proof of copyright clearance.

Quota limits return `quota_wait` until the next Pacific midnight. Failed authorization holds in `auth_required` until credentials change. Transient failures persist a next-attempt time and a cumulative failure count; exhausting the configured cross-cycle retry allowance requires review. Long server `Retry-After` intervals are persisted without keeping a process asleep for hours. Permanent rejection returns `permanent_error`. Approval, media, checksum, and schedule issues return `needs_review` without aborting the whole batch. Keep the machine awake and revisit review states. The worker must hold its OS file lock throughout upload and polling. Multiple workers would need transactional claims/leases in addition to unique publication intentions.

## Owner data retention and withdrawal

Other Authorized Data must be refreshed or deleted within 30 days. In-client consent revocation requires immediate programmatic revocation and deletion within seven days; security-page revocation requires periodic refresh validation and deletion within 30 days. User-requested deletion must occur within seven days. [Official developer policies, III.D.2.3 and III.E.4](https://developers.google.com/youtube/terms/developer-policies).

This starter is for one local operator and one configured owner channel. Pending processing/publication polls respect `upload.poll_every_minutes`; settled records refresh every 28 days. On the next worker invocation, unrefreshed remote IDs, states, offsets, and URIs older than 30 days are removed and the local intention requires reconciliation. A rejected refresh token immediately deletes the owner's upload API records and token. Run the worker regularly; software cannot physically erase a disk while the computer is off. Apply the same lifecycle to private backups and any exported API data.

Run `python -m clipforge --config config.json revoke` to request remote consent revocation and delete local upload account data, or `delete-owned-data` for local deletion only. Both remove publication records and the token, leaving only irreversible hashes of local clip/channel intentions to prevent accidental reinsertion. These commands do not delete videos on YouTube or the operator's original/prepared local files. Review the reported `revocation_confirmed` field; if revocation could not be confirmed, remove consent through [Google Account permissions](https://security.google.com/settings/security/permissions). Local-file deletion and remote-video deletion are distinct operations.

## Verification scope

The supplied upload tests use synthetic bytes and mocked HTTP sessions. They cover interrupted-process recovery, lost-final-response recovery, refusal to duplicate an expired/ambiguous session, preparation approval gates, exact channel checking, checksum mismatches, invalid schedules, and processing/publication separation. No real OAuth consent, Google token refresh, or YouTube upload was performed during creation of this starter.
